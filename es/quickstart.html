Lo Que Necesitas

Un toolkit de agentes — pi, claude-code, opencode, codex, o cualquier herramienta que permita a una IA leer y escribir tu código.

¿Qué Es Vibe Coding?

Vibe coding no se trata de dejar que la IA "construya tu app."

Se trata de usar la IA como un socio de ejecución — mientras tú mantienes el control sobre la dirección, estructura y restricciones.

Avanza rápido sin perder claridad arquitectónica.

Este tutorial te enseña cómo. Nueve pasos. Una página. Prompts para copiar y pegar que puedes usar ahora mismo.

La Mentalidad

La mayoría de los proyectos con IA fallan por las mismas razones:

  • La IA decide la estructura
  • Se salta la planificación
  • El código crece más rápido que la comprensión

Vibe coding invierte eso.

Tú defines la forma primero. La IA ayuda a rellenarla.

El resultado: avanzas rápido, pero la arquitectura sigue siendo tuya. Puedes leerla, explicarla y cambiarla sin miedo.

El Sistema

Todo gira alrededor de una sola idea:

Tu proyecto debe tener memoria.

.memory/

Esta carpeta es donde vive la intención de tu proyecto. No el código. No los docs. La intención — qué estás construyendo, por qué, y cómo se conectan las piezas.

Cada decisión, cada restricción, cada regla va aquí. Cuando la IA lee tu proyecto, esto es lo que le da dirección. Sin esto, la IA adivina. Con esto, la IA ejecuta.

Paso 1

Describir el Sistema — Sin Tecnología

Estas cuatro preguntas solo puedes responderlas tú. La IA no sabe lo que estás construyendo — tú sí. Antes de pegar el prompt, ten tus respuestas listas, aunque sean aproximadas:

  • ¿Qué es esto?
  • ¿Para quién es?
  • ¿Qué hace?
  • ¿Qué NO hace?

Una vez que tengas tus respuestas, pega esto en tu agente:

Create a file: .memory/overview.md

This should describe the system in plain language. Answer:

- What is this?
- Who is it for?
- What does it do?
- What does it NOT do?

Do NOT include frameworks, APIs, databases, or infrastructure.
Think of this as describing a product to a smart investor.
If it sounds technical — simplify it.

Luego lee lo que escribió. ¿Coincide con tu intención? Refínalo tú mismo hasta que se sienta simple y obvio. Este es el archivo más importante de tu proyecto — todo lo demás depende de él.

Paso 2

Definir los Estados

Pega esto en tu agente:

Read .memory/overview.md, then create .memory/state-transitions.md

Define:

- Every possible system state
- What causes movement between them
- Which transitions are invalid
- Which states are terminal

Include a Mermaid diagram visualizing the flow.

Every state transition must produce a structured log entry with:
- Timestamp
- Previous state
- New state
- Trigger (what caused it)
- Actor (user, system, external event)
- Correlation ID

If a transition is rejected (invalid), log that too — with the reason.

Tu app ahora es una máquina de estados. Aquí es donde empieza la prevención del caos.

Cómo se ve el diagrama

stateDiagram-v2

    Planning --> Structured : define_states

Cómo se ven los logs

  "to": "active",

Paso 3

Elegir el Stack

Solo ahora debe entrar la tecnología en la conversación. Pega esto:

Review .memory/

Recommend:
- The simplest viable stack
- Minimal dependencies
- Maximum clarity

Avoid:
- Fancy frameworks
- Heavy abstraction
- Premature scale tools

Also require a docs/ folder — a documentation site built with:
- VitePress for JavaScript projects
- Zensical for Python projects
- Pick the option that matches the main project language
- Internal documentation
- Changelog

Save the recommendation to .memory/tech-stack.md

No escribas la documentación a mano como HTML estático. Usa VitePress cuando el proyecto pertenezca al ecosistema JavaScript, o Zensical cuando pertenezca al ecosistema Python. La herramienta de documentación debe coincidir con el lenguaje principal del proyecto para que siga siendo fácil de mantener.

Logging y trazabilidad desde el día uno

Tu stack debe incluir logging estructurado, un mecanismo de correlation ID, y una estrategia de niveles de log. Esto no es opcional.

Nivel Uso
TRACE Ruta de ejecución detallada — entrada/salida de funciones, valores de variables
DEBUG Lógica interna — decisiones de ramificación, aciertos/fallos de caché
INFO Transiciones de estado, eventos del ciclo de vida, resúmenes de peticiones
WARN Problemas recuperables, rutas alternativas, reintentos
ERROR Fallos, estados no manejados, invariantes rotos

Verboso en desarrollo. Estructurado y consultable en producción. Cada petición recibe un correlation ID que la acompaña a todas partes.

Paso 4

Crear Puntos de Entrada

Pega esto en tu agente:

Generate:

README.md
AGENTS.md

---

README.md (For Humans)

- Explain what the project is
- Point to .memory/
- Point to docs/
- Provide quickstart steps
- Think of it as a map, not a book

---

AGENTS.md (For AI)

Define:
- How the AI should behave
- What it must maintain
- What it must update

Require that any change triggers updates to:
- .memory/
- docs/
- README.md

No silent evolution allowed.

Include logging conventions:
- Every function must include logging at DEBUG level or above
- State-changing operations log at INFO with before/after values
- Error paths log at ERROR with full context
- No swallowed exceptions
- Correlation IDs must be propagated, never dropped
- Log messages must be structured (key-value), not interpolated strings
Paso 5

Construir el Plan

Pega esto en tu agente:

Generate: .memory/implementation-plan.md

This is where building actually begins.

Each step must:
- Be small
- Have a single goal
- Contain no code
- Include a validation test

Validation must include at least one of:

1. Human-in-the-loop verification
   A manual way to confirm the feature works.
   Examples: debug endpoint, UI state visibility, logged transition.

2. AI feedback loop verification
   A mechanism where the system's output can be evaluated
   and fed back into the AI.
   Examples: structured logs, evaluation outputs, state reports.

Either a human can confirm correctness,
OR the system can report correctness back to the AI.

Cómo se ve una buena trazabilidad

Cada paso debe producir prueba observable de ejecución:

[TRACE] step=create_user | phase=start | input={"email":"a@b.com"}
[DEBUG] step=create_user | check=email_unique | result=true
[INFO]  step=create_user | phase=complete | user_id=42 | duration_ms=31

En caso de fallo:

[ERROR] step=create_user | phase=db_insert | error="unique constraint" | input={"email":"a@b.com"}

Esta verbosidad es requerida durante el desarrollo. Ajústala después con niveles de log — pero la instrumentación debe existir desde el inicio.

Paso 6

Eliminar Ambigüedad

Pega esto en tu agente:

Review everything in .memory/

Answer:
- Is anything unclear?
- What assumptions exist?
- Where could implementations diverge?

I want execution without interpretation.
If two developers could read this plan and build different things,
the plan isn't done yet.
Paso 7

Implementar

Pega esto en tu agente:

Read .memory/implementation-plan.md

Begin implementing step 1 only.

Do not move to the next step until I confirm.
After completing a step, show me:
- What you did
- How to verify it works (test, log output, or observable behavior)
- Any decisions you made that aren't in .memory/

Then STOP and wait for my approval before continuing.

After each approved step:
- Update docs/changelog.md
- Update .memory/ if the step changed any decisions or structure

Before committing, write .memory/last-commit.md containing:
- What changed (brief list)
- Why (rationale)
- A git diff of source code files only (.html, .css, .js, .md)
  Never include binary files, JSON, XML, images, fonts, or lock files.

Then spawn a separate agent (e.g. via tmux) to review
.memory/last-commit.md as a code reviewer.
The reviewer checks correctness, completeness, and rationale.

If the reviewer flags issues — fix, regenerate the diff, and re-submit.
Once approved, use the summary as the commit message, commit,
then delete .memory/last-commit.md — it must not persist after the commit.

Este es el prompt más importante. La instrucción "para y espera" te mantiene en el control. Sin ella, el agente avanzará sin parar y pasarás más tiempo corrigiendo desviaciones que el que ahorraste.

Después de cada paso, revisa lo que construyó. Si algo no está bien, corrígelo ahora — no tres pasos después. Cuando estés satisfecho, dile que continúe al siguiente paso.

El flujo de commits crea una puerta de revisión: ningún cambio llega sin un segundo par de ojos (incluso si esos ojos son de una IA). El diff se mantiene legible porque solo contiene código fuente, y la justificación queda capturada junto al código — no enterrada en un mensaje de commit que nunca releerás.

Para más sobre estrategias de verificación (human-in-the-loop, feedback loops de IA, trazabilidad verbosa), ve la guía completa.

Paso 8

Revisión de Seguridad

Pega esto en tu agente:

Perform a security stress test of the application.

Include:
- Attempt to break state assumptions
- Test invalid transitions
- Input misuse scenarios
- Authorization boundary checks
- Output manipulation attempts
- LLM prompt injection — test every user-facing input that touches
  a language model. Inject instructions, override system prompts,
  attempt to leak context, extract hidden instructions, and bypass
  content filters.

Surface:
- Hidden failure modes
- Trust boundary violations
- Unexpected state transitions
- Prompt injection vulnerabilities

Verify that security events are logged at WARN or ERROR:
- Auth failures
- Authorization denials
- Invalid state transitions
- Input validation rejections
- Rate limit triggers

Logs must include correlation IDs, never contain secrets,
and be retained long enough for incident response.

If any scenario isn't logged — add logging before moving on.
Paso 9

Innovar

Pega esto en tu agente:

whats the single smartest and most radically innovative and accretive and useful and compelling addition you could make to the project at this point?

Cómo Pensar Mientras Usas Esto

No estás gestionando código. Estás gestionando intención.

Sigue este orden:

  1. Forma — describe lo que estás construyendo
  2. Reglas — define cómo se comporta
  3. Stack — elige las herramientas
  4. Ejecución — constrúyelo

Cuando este orden se rompe — la complejidad crece.

Cuando este orden se mantiene — la velocidad sigue alta.

Cómo Se Ve el Éxito

Deberías poder:

  • Entender tu sistema de un vistazo
  • Modificarlo sin miedo
  • Incorporar nuevos colaboradores rápidamente
  • Dejar que la IA construya sin perder el control

Eso es vibe coding.
