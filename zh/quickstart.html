你需要什么

一个智能体工具 — pi、claude-code、opencode、codex，或任何能让AI读写你代码库的工具。

什么是 Vibe Coding？

Vibe coding 不是让AI"帮你写应用"。

而是把AI当作执行伙伴——同时你保持对方向、结构和约束的控制。

快速前进，不失去架构清晰度。

这个教程教你怎么做。九个步骤。一个页面。可以立即使用的复制粘贴提示词。

心态

大多数AI驱动的项目失败的原因都一样：

  • AI决定了结构
  • 跳过了规划
  • 代码增长速度超过了理解速度

Vibe coding 反转了这一点。

你先定义形状。AI帮你填充。

结果：你快速前进，但架构仍然是你的。你可以阅读它、解释它、毫无恐惧地修改它。

系统

一切围绕一个核心概念：

你的项目必须有记忆。

.memory/

这个文件夹是你项目意图的所在。不是代码库。不是文档。而是意图——你在构建什么、为什么，以及各部分如何连接。

每个决策、每个约束、每条规则都放在这里。当AI阅读你的项目时，这就是给它方向的东西。没有它，AI靠猜。有了它，AI去执行。

第1步

描述系统——不用技术术语

这四个问题只有你能回答。AI不知道你在构建什么——你知道。在粘贴提示词之前，先准备好你的答案，哪怕是粗略的：

  • 这是什么？
  • 为谁而做？
  • 它做什么？
  • 它不做什么？

当你有了答案后，将此粘贴到你的智能体中：

Create a file: .memory/overview.md

This should describe the system in plain language. Answer:

- What is this?
- Who is it for?
- What does it do?
- What does it NOT do?

Do NOT include frameworks, APIs, databases, or infrastructure.
Think of this as describing a product to a smart investor.
If it sounds technical — simplify it.

然后阅读它写的内容。它符合你的意图吗？自己修改，直到感觉简单明了。这是你项目中最重要的文件——后续一切都依赖于它。

第2步

定义状态

将此粘贴到你的智能体中：

Read .memory/overview.md, then create .memory/state-transitions.md

Define:

- Every possible system state
- What causes movement between them
- Which transitions are invalid
- Which states are terminal

Include a Mermaid diagram visualizing the flow.

Every state transition must produce a structured log entry with:
- Timestamp
- Previous state
- New state
- Trigger (what caused it)
- Actor (user, system, external event)
- Correlation ID

If a transition is rejected (invalid), log that too — with the reason.

你的应用现在是一个状态机。混乱的预防从这里开始。

图表长什么样

stateDiagram-v2
    [*] --> Idle
    Idle --> Planning : describe_system
    Planning --> Structured : define_states
    Structured --> Ready : choose_stack
    Ready --> Building : implement
    Building --> Review : step_complete
    Review --> Building : next_step
    Review --> Done : all_steps_pass
    Done --> [*]

日志长什么样

{
  "ts": "2026-03-01T09:34:00Z",
  "correlation_id": "abc-123",
  "actor": "user:42",
  "from": "pending",
  "to": "active",
  "trigger": "payment_confirmed",
  "metadata": {}
}
第3步

选择技术栈

只有现在才应该让技术进入对话。粘贴这个：

Review .memory/

Recommend:
- The simplest viable stack
- Minimal dependencies
- Maximum clarity

Avoid:
- Fancy frameworks
- Heavy abstraction
- Premature scale tools

Also require a docs/ folder — a documentation site built with:
- VitePress for JavaScript projects
- Zensical for Python projects
- Pick the option that matches the main project language
- Internal documentation
- Changelog

Save the recommendation to .memory/tech-stack.md

不要把文档手写成静态HTML。项目属于 JavaScript 生态时使用 VitePress，属于 Python 生态时使用 Zensical。文档工具应该与项目的主要语言保持一致，这样文档才容易维护。

从第一天起就要有日志和追踪

你的技术栈必须包含结构化日志、关联ID机制和日志级别策略。这不是可选的。

级别 用途
TRACE 细粒度执行路径——函数入口/出口、变量值
DEBUG 内部逻辑——分支决策、缓存命中/未命中
INFO 状态转换、生命周期事件、请求摘要
WARN 可恢复问题、回退路径、重试
ERROR 故障、未处理状态、不变量破坏

开发环境要详细。生产环境要结构化可查询。每个请求都有一个关联ID，跟随它到各处。

第4步

创建入口点

将此粘贴到你的智能体中：

Generate:

README.md
AGENTS.md

---

README.md (For Humans)

- Explain what the project is
- Point to .memory/
- Point to docs/
- Provide quickstart steps
- Think of it as a map, not a book

---

AGENTS.md (For AI)

Define:
- How the AI should behave
- What it must maintain
- What it must update

Require that any change triggers updates to:
- .memory/
- docs/
- README.md

No silent evolution allowed.

Include logging conventions:
- Every function must include logging at DEBUG level or above
- State-changing operations log at INFO with before/after values
- Error paths log at ERROR with full context
- No swallowed exceptions
- Correlation IDs must be propagated, never dropped
- Log messages must be structured (key-value), not interpolated strings
第5步

制定计划

将此粘贴到你的智能体中：

Generate: .memory/implementation-plan.md

This is where building actually begins.

Each step must:
- Be small
- Have a single goal
- Contain no code
- Include a validation test

Validation must include at least one of:

1. Human-in-the-loop verification
   A manual way to confirm the feature works.
   Examples: debug endpoint, UI state visibility, logged transition.

2. AI feedback loop verification
   A mechanism where the system's output can be evaluated
   and fed back into the AI.
   Examples: structured logs, evaluation outputs, state reports.

Either a human can confirm correctness,
OR the system can report correctness back to the AI.

好的追踪长什么样

每一步都应该产生可观测的执行证据：

[TRACE] step=create_user | phase=start | input={"email":"a@b.com"}
[DEBUG] step=create_user | check=email_unique | result=true
[INFO]  step=create_user | phase=complete | user_id=42 | duration_ms=31

失败时：

[ERROR] step=create_user | phase=db_insert | error="unique constraint" | input={"email":"a@b.com"}

这种详细程度在开发期间是必须的。之后通过日志级别调低——但从一开始就必须有这些检测。

第6步

消除歧义

将此粘贴到你的智能体中：

Review everything in .memory/

Answer:
- Is anything unclear?
- What assumptions exist?
- Where could implementations diverge?

I want execution without interpretation.
If two developers could read this plan and build different things,
the plan isn't done yet.
第7步

实施

将此粘贴到你的智能体中：

Read .memory/implementation-plan.md

Begin implementing step 1 only.

Do not move to the next step until I confirm.
After completing a step, show me:
- What you did
- How to verify it works (test, log output, or observable behavior)
- Any decisions you made that aren't in .memory/

Then STOP and wait for my approval before continuing.

After each approved step:
- Update docs/changelog.md
- Update .memory/ if the step changed any decisions or structure

Before committing, write .memory/last-commit.md containing:
- What changed (brief list)
- Why (rationale)
- A git diff of source code files only (.html, .css, .js, .md)
  Never include binary files, JSON, XML, images, fonts, or lock files.

Then spawn a separate agent (e.g. via tmux) to review
.memory/last-commit.md as a code reviewer.
The reviewer checks correctness, completeness, and rationale.

If the reviewer flags issues — fix, regenerate the diff, and re-submit.
Once approved, use the summary as the commit message, commit,
then delete .memory/last-commit.md — it must not persist after the commit.

这是最重要的提示词。"停下来等待"的指令让你保持在控制中。没有它，智能体会一路冲刺，你花在修复偏差上的时间会比省下的时间更多。

每一步之后，检查它构建了什么。如果有什么不对，现在就纠正——不要三步之后再说。当你满意时，告诉它继续下一步。

提交工作流创建了一个审查关卡：没有经过第二双眼睛（即使那双眼睛是 AI 的）的检查，任何变更都不会通过。差异保持可读性，因为它只包含源代码，而理由与代码一起被记录——而不是埋在你永远不会重新阅读的提交信息中。

关于验证策略（人工确认、AI反馈循环、详细追踪）的更多信息，请查看完整指南。

第8步

安全审查

将此粘贴到你的智能体中：

Perform a security stress test of the application.

Include:
- Attempt to break state assumptions
- Test invalid transitions
- Input misuse scenarios
- Authorization boundary checks
- Output manipulation attempts
- LLM prompt injection — test every user-facing input that touches
  a language model. Inject instructions, override system prompts,
  attempt to leak context, extract hidden instructions, and bypass
  content filters.

Surface:
- Hidden failure modes
- Trust boundary violations
- Unexpected state transitions
- Prompt injection vulnerabilities

Verify that security events are logged at WARN or ERROR:
- Auth failures
- Authorization denials
- Invalid state transitions
- Input validation rejections
- Rate limit triggers

Logs must include correlation IDs, never contain secrets,
and be retained long enough for incident response.

If any scenario isn't logged — add logging before moving on.
第9步

创新

将此粘贴到你的智能体中：

whats the single smartest and most radically innovative and accretive and useful and compelling addition you could make to the project at this point?

使用时如何思考

你不是在管理代码。你是在管理意图。

按这个顺序：

  1. 形状 — 描述你在构建什么
  2. 规则 — 定义它如何运行
  3. 技术栈 — 选择工具
  4. 执行 — 构建它

当这个顺序被打破——复杂性增长。

当这个顺序保持——速度保持高效。

成功是什么样的

你应该能够：

  • 一眼理解你的系统
  • 毫无恐惧地修改它
  • 快速让新贡献者上手
  • 让AI构建而不失去控制

这就是 vibe coding。
