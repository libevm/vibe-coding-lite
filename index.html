What You Need

An agent toolkit — pi, claude-code, opencode, codex, or any tool that lets an AI read and write your codebase.

What Is Vibe Coding?

Vibe coding is not about letting AI "build your app."

It's about using AI as an execution partner — while you retain control over direction, structure, and constraints.

Move fast without losing architectural clarity.

This vibe coding tutorial teaches you how. Eight steps. One page. Copy-paste prompts you can use right now.

The Mindset

Most AI-driven projects fail for the same reasons:

  • The AI decides structure
  • Planning is skipped
  • Code grows faster than understanding

Vibe coding flips that.

You define the shape first. AI helps fill it in.

The result: you move fast, but the architecture stays yours. You can read it, explain it, and change it without fear.

The System

Everything revolves around a single idea:

Your project must have a memory.

.memory/

This folder is where your project's intent lives. Not the codebase. Not the docs. The intent — what you're building, why, and how the pieces connect.

Every decision, every constraint, every rule goes here. When the AI reads your project, this is what gives it direction. Without it, the AI guesses. With it, the AI executes.

Step 1

Describe the System — Without Tech

Paste this into your agent:

Create a file: .memory/overview.md

This should describe the system in plain language. Answer:

- What is this?
- Who is it for?
- What does it do?
- What does it NOT do?

Do NOT include frameworks, APIs, databases, or infrastructure.
Think of this as describing a product to a smart investor.
If it sounds technical — simplify it.

Then read what it wrote. Refine it yourself until it feels simple and obvious. This is the most important file in your project — everything downstream depends on it.

Step 2

Define the States

Paste this into your agent:

Read .memory/overview.md, then create .memory/state-transitions.md

Define:

- Every possible system state
- What causes movement between them
- Which transitions are invalid
- Which states are terminal

Include a Mermaid diagram visualizing the flow.

Every state transition must produce a structured log entry with:
- Timestamp
- Previous state
- New state
- Trigger (what caused it)
- Actor (user, system, external event)
- Correlation ID

If a transition is rejected (invalid), log that too — with the reason.

Your app is now a state machine. This is where chaos prevention starts.

Step 3

Choose the Stack

Only now should tech enter the conversation. Paste this:

Review .memory/

Recommend:
- The simplest viable stack
- Minimal dependencies
- Maximum clarity

Avoid:
- Fancy frameworks
- Heavy abstraction
- Premature scale tools

Also require a docs/ folder that will contain:
- Internal documentation
- Changelog

Save the recommendation to .memory/tech-stack.md

Logging and tracing from day one

Your stack must include structured logging, a correlation ID mechanism, and a log level strategy. This is not optional.

Level Use
TRACE Fine-grained execution path — function entry/exit, variable values
DEBUG Internal logic — branching decisions, cache hits/misses
INFO State transitions, lifecycle events, request summaries
WARN Recoverable issues, fallback paths, retries
ERROR Failures, unhandled states, broken invariants

Verbose in development. Structured and queryable in production. Every request gets a correlation ID that follows it everywhere.

Step 4

Create Entry Points

Paste this into your agent:

Generate:

README.md
AGENTS.md

---

README.md (For Humans)

- Explain what the project is
- Point to .memory/
- Point to docs/
- Provide quickstart steps
- Think of it as a map, not a book

---

AGENTS.md (For AI)

Define:
- How the AI should behave
- What it must maintain
- What it must update

Require that any change triggers updates to:
- .memory/
- docs/
- README.md

No silent evolution allowed.

Include logging conventions:
- Every function must include logging at DEBUG level or above
- State-changing operations log at INFO with before/after values
- Error paths log at ERROR with full context
- No swallowed exceptions
- Correlation IDs must be propagated, never dropped
- Log messages must be structured (key-value), not interpolated strings
Step 5

Build the Plan

Paste this into your agent:

Generate: .memory/implementation-plan.md

This is where building actually begins.

Each step must:
- Be small
- Have a single goal
- Contain no code
- Include a validation test

Validation must include at least one of:

1. Human-in-the-loop verification
   A manual way to confirm the feature works.
   Examples: debug endpoint, UI state visibility, logged transition.

2. AI feedback loop verification
   A mechanism where the system's output can be evaluated
   and fed back into the AI.
   Examples: structured logs, evaluation outputs, state reports.

Either a human can confirm correctness,
OR the system can report correctness back to the AI.

What good tracing looks like

Each step should produce observable proof of execution:

[TRACE] step=create_user | phase=start | input={"email":"a@b.com"}
[DEBUG] step=create_user | check=email_unique | result=true
[INFO]  step=create_user | phase=complete | user_id=42 | duration_ms=31

On failure:

[ERROR] step=create_user | phase=db_insert | error="unique constraint" | input={"email":"a@b.com"}

This verbosity is required during development. Dial it back later via log levels — but the instrumentation must exist from the start.

Step 6

Remove Ambiguity

Paste this into your agent:

Review everything in .memory/

Answer:
- Is anything unclear?
- What assumptions exist?
- Where could implementations diverge?

I want execution without interpretation.
If two developers could read this plan and build different things,
the plan isn't done yet.
Step 7

Implement

Paste this into your agent:

Read .memory/implementation-plan.md

Begin implementing step 1 only.

Do not move to the next step until I confirm.
After completing a step, show me:
- What you did
- How to verify it works (test, log output, or observable behavior)
- Any decisions you made that aren't in .memory/

Then STOP and wait for my approval before continuing.

After each approved step:
- Update docs/changelog.md
- Update .memory/ if the step changed any decisions or structure

This is the most important prompt. The "stop and wait" instruction keeps you in the loop. Without it, the agent will sprint through the plan and you'll spend more time fixing drift than you saved.

After each step, review what it built. If something is off, correct it now — not three steps later. When you're satisfied, tell it to continue to the next step.

For more on verification strategies (human-in-the-loop, AI feedback loops, verbose tracing), see the full guide.

Step 8

Security Pass

Paste this into your agent:

Perform a security stress test of the application.

Include:
- Attempt to break state assumptions
- Test invalid transitions
- Input misuse scenarios
- Authorization boundary checks
- Output manipulation attempts
- LLM prompt injection — test every user-facing input that touches
  a language model. Inject instructions, override system prompts,
  attempt to leak context, extract hidden instructions, and bypass
  content filters.

Surface:
- Hidden failure modes
- Trust boundary violations
- Unexpected state transitions
- Prompt injection vulnerabilities

Verify that security events are logged at WARN or ERROR:
- Auth failures
- Authorization denials
- Invalid state transitions
- Input validation rejections
- Rate limit triggers

Logs must include correlation IDs, never contain secrets,
and be retained long enough for incident response.

If any scenario isn't logged — add logging before moving on.

How to Think While Using This

You are not managing code. You are managing intent.

Follow this order:

  1. Shape — describe what you're building
  2. Rules — define how it behaves
  3. Stack — choose the tools
  4. Execution — build it

When this order breaks — complexity grows.

When this order holds — velocity stays high.

What Success Looks Like

You should be able to:

  • Understand your system at a glance
  • Modify it without fear
  • Onboard new contributors quickly
  • Let AI build without losing control
